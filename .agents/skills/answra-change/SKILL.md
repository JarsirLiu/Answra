# Answra 工程 Note 流程

## 开始前

1. 阅读根目录 `AGENTS.md` 和 `docs/README.md`。
2. 在 `docs/notes/` 查找相关功能、模块和历史问题，先确认已有决定以及明确禁止的回退。
3. 对功能新增、删除、用户行为变化、跨模块契约、架构、依赖、持久化、测试策略、工程流程和有复盘价值的缺陷，先新增或更新 Note，再改代码。
4. 一项变更有多个独立功能或决策时分别写 Note，不能用一条泛化记录覆盖所有取舍。
5. Note 必须写清问题、影响范围、决定、真实备选方案及舍弃原因、后果，以及验证证据或防回退约束。

## Note 生命周期

- `proposed/`：待评审方案。
- `implemented/`：已经交付的决定，必须与当前代码一致。
- `rejected/`：明确拒绝但未来可能重复出现的方案，保留拒绝原因。
- `archived/`：已经失去未来指导价值的已实施 Note；安全边界和防回退依据不得归档。

路径格式：`docs/notes/<状态>/<类别>/YYYY-MM-DD-主题.md`。类别为 `feature`、`bug-fix`、`simplification`、`architecture`、`process`、`testing`。正文使用中文，稳定代码标识保留英文。

## 完成前

1. 添加或更新对应测试，并确认所有代码行为与 Note 一致。
2. 运行 `pnpm notes:check` 和 `pnpm verify`。
3. 原生窗口、捕获保护、权限等平台行为要区分自动化测试与系统实测，并写明平台、版本和证据。
4. 提案实施后迁移到 `implemented/` 并改写为实际结果；不能把未实施的规划留在已实施 Note 中。

纯格式、typo 和不改变行为的机械重命名可以不新增 Note，但仍需通过门禁。
