# Note：回复条原地切换回复态

状态：已实施

## 问题

确认发送后，回复条虽然已经使用独立的 `BrowserWindow`，但右侧关闭按钮会直接结束截图工作流并恢复悬浮导航栏。用户无法在同一条消息表面取消当前回复后继续截图，且流式文本的布局容易让回复条显得过长。

## 涉及范围

- `packages/ui/src/components/panels/ReplyBar.tsx`
- `packages/ui/src/app/useReplyWorkflow.ts`
- `packages/ui/src/app/ReplyBarWindowApp.tsx`
- `packages/shared/src/channels.ts`
- `apps/desktop/src/main/ipc/windowIpc.ts`

## 决定

回复条继续作为一个独立、受捕获保护的窗口；发送后只在这个窗口内部把 `composing` 替换为 `streaming`。回复态右侧按钮发送 `cancel`，清空当前演示回复并回到 `composing`，不结束工作流、不恢复主导航栏。发送态可以再次点击“继续截图”并重新发送。

回复展示使用固定的短条布局，文本只在内部单行滚动，不参与窗口的无限扩宽；取消按钮沿用 `SurfaceButton` 和现有关闭图标体系。

## 影响表面

- 发送态：截图缩略图、继续截图、确认发送和关闭。
- 回复态：短条内显示回复文本，右侧取消按钮返回发送态。
- 独立回复窗口：发送态和回复态共用同一个受捕获保护的 `BrowserWindow`。

## 曾考虑的替代方案

- **取消时直接关闭回复窗口**：交互成本低，但无法满足用户在同一条上继续截图的需求，也会让主导航栏抢回表面，因此舍弃。
- **为回复态另建一个窗口**：会增加窗口生命周期、隐身保护和主题同步边界，无法解决同一工作流的状态连贯性，因此舍弃。
- **保留长文本自适应宽度**：回复内容会改变原生窗口尺寸，破坏短条定位和稳定的隐身窗口生命周期，因此舍弃。

## 后果与防回退

- `ReplyBarAction` 新增 `cancel`，main 侧必须继续校验并转发该动作。
- `cancel` 只改变工作流阶段；真正放弃工作流仍使用 `close`。
- 回复窗口仍独立存在，不能把回复条合并回主窗口或通过隐藏主窗口承载回复内容。

## 验证

- UI 测试覆盖发送后进入回复态、取消后回到发送态以及再次截图入口。
- `pnpm verify` 和 `pnpm notes:check` 作为交付门禁。
- Windows 捕获保护仍需在 Electron 29.4.6 的真实桌面环境验证；自动化测试只验证状态和 IPC 契约。
