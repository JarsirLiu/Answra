# Answra 代码规范

**用法：** 写代码前读"上篇"；写的过程中对"中篇"每一条负责；写完后按下篇与终篇自查。评审他人（含 AI）产出的代码时，四篇逐条核对，缺一即驳。

**总纲一句话：少而可信，胜过多而可疑。** 一切条款都在治同一个病——AI 用代码产量证明自己"完成了任务"。任务完成的唯一标准是事实成立、行为可验证、人可以放心维护。

**最高纪律，凌驾于所有其它条款与任何紧迫度之上：任何情况下不得为完成用户需求而违反本规范。** "用户在催"、"需求赶交付"、"既有代码也这么写"、"这样最快"——全都不是降低标准的理由。宁可按 §1 停下并客观报告缺口，也绝不交付看起来功能正常、内部却不合理的代码。**那种代码不是完成，是负资产**：它把不规范伪装成已交付的事实，由整个团队照它的样子继续堆，屎山就是这样养成的。停下报告是合格产出，减配完成度不是。

**优先级：** AGENTS.md（结构组织）> 本规范（代码质量）> 个人风格。若本规范与 AGENTS.md 或实施中的 Note 冲突，以最近的决策文件为准，并回修本规范。字面越界由 `pnpm architecture:check`、typecheck、biome 机械兜底；判断类条款（状态来源、抽象时机、规模例外）由自查与评审执行。

# 上篇 · 能不能动笔

## 1. 前置条件闸门（事实不足 = 停止，不写）

"完成"是指事实成立的完成，不是代码写完。前置不足仍然动笔，产出的就是建立在不存在的链路上的假功能。

**准入：依据必须读出来。** 动手前把依赖的现实核一遍——读代码、读测试、读相关 Note、查包导出表。每个前提能对上三者之一才算成立：

| 依据 | 形态 |
|---|---|
| 当前代码 | 已经存在的实现/测试，可直接引用路径 |
| 已合并契约 | `channels.ts`、`protocol.ts`、领域 contracts、端口定义 |
| 用户明说 | 需求里明确授权的行为；其余一律视为未决 |

推断（"按惯例应该有"、"大概是个 map"、"上游肯定返回这个"）永远不是依据。

**四种强行完成手法，发现即停止：**

1. **杜撰接口**：mock 或假写"应该存在"的上游 API、字段、行为、调用链；
2. **吞断链路**：用 `?.`、try-catch、默认值把接不上的链路咽下去，装作整条链路能跑；
3. **顺手重造**：找不到期望的工具就自己造一个，制造双真相源与隐性裂缝；
4. **顺猜下游**：沿着猜测的接口先把下游写完，赌它"以后对上"。

**停下的输出格式（缺前置时唯一合法的产出）：** 用用户能懂的语言报告，四段齐全：

1. 需求的哪一步现在做不到，判断来源是哪段代码/契约/测试与现实期望不符；
2. 缺失前置清单：每条写"它是什么、为什么是前置、当前缺什么证据"；
3. 可选路径：按序补齐前置（各自代价），或收窄本次任务范围；
4. 措辞红线：不说"应该可以"、"先这样、后面再对"；一切推测显式标注为推测。

**多步需求照实展开：** 用户提一个需求，若底层要先有契约、存储、IPC、权限等 N 步，把完整链路（建立在什么之上、现状、各自代价）列给用户确认；未确认的步骤不预写、不"顺手实现"。默认用户不懂代码，因此链条必须翻译成产品语言。

**"完成"的定义：** 行为可验证（测试或实机证据与真实需求一致）才算完成；编译通过、类型全绿只是及格线；总结里不得把未决事实混进"已完成"叙述。

## 2. 代码归属（落层判断）

写任何文件之前，先回答它属于哪一行、禁止带什么：

| 层 | 只放 | 禁止携带 |
|---|---|---|
| `packages/shared` | 跨进程契约：`channels.ts`、`env.ts`、跨包类型与常量 | 业务逻辑、平台依赖 |
| `packages/ui` | 纯展示与可复用组件、组件测试 | import electron/node、领域分支 |
| `desktop/src/main` | Electron / node 平台能力：窗口、IPC handler、采集、注入、IME host | 只为 renderer 用的纯算法（应进 shared） |
| `desktop/src/preload` | `contextBridge` 转发 | 任何业务逻辑 |
| `desktop/src/renderer` | 应用薄壳、挂载入口 | electron/node 模块 |
| `agent/src/core` | 第二位消费者出现后的跨领域底座 | 领域产品策略；第一位消费者不得预留 |
| `agent/src/worker` | 线协议类型（唯一） | 算法、领域逻辑 |
| `agent/src/<domain>` | 领域运行时、领域 contracts、领域组合根和对接 | 平台实现（持端口，由 desktop 注入） |

**口诀：** 沾 Electron/node 进 desktop；换端还通用进 shared/ui；跨领域共享先等第二消费者；其余进领域平级目录。**组合根只接线不实现**；模块不 import 平台、不 `new` 平台实现——真实实现（采集、注入、存储）由 desktop main 或领域 `runtime.ts` 在组合根注入，领域代码永远只认识端口接口（榜例：`host.ts` 的 worker factory、`startAgentHost` 都在边界上接线）。

# 中篇 · 怎么写才合规

## 3. 契约与类型纪律

- **一处定义，处处引用。** ID 与值对象用品牌类型 + 校验工厂（榜例 `contracts.ts`：`Brand<T, Name>`、`sessionId()/conversationId()` 工厂产出 `__brand`，禁止手工转型）；跨进程字符串 ID 不允许裸传。
- **契约文件唯一：** 频道常量与请求/响应映射只在 `packages/shared/src/channels.ts`；agent 线协议只在 `worker/protocol.ts`；领域契约只在 `<domain>/contracts.ts`。
- **DTO 逐层投影：** domain 事件 → worker DTO → renderer DTO 各建类型，显式投影函数翻译（榜例 `interviewProjection.ts`），不把内部类型直接 expose 成 IPC 载荷。
- **语义用字面量联合 + JSDoc 逐值说明**（如 `TranscriptEvent.kind: "partial" | "chunk-final" | "error"`），不用数字枚举。
- **禁 `any`**；`unknown` 只允许出现在真正未知边界（解析外部输入）并立即收窄——收不窄 = 契约没想清，回 §1。
- **新概念先落类型和边界，再写实现**：多人并行与测试先行才有抓手。

## 4. 状态与行为的显式来源（"功能看起来正常"不算合规）

推演状态是隐性的杜撰接口：链路不存在，靠代码补出表象，短期看到了功能，长期看不到可维护性。**没有协议来源的状态 = 前置条件不足 → 回 §1 停下，先立契约。**

- **状态三问（每个被消费的字段必答）：** 谁写它（唯一 writer）；从哪来（显式来源四选一：store 端口方法 / worker 事件帧 / 用户输入 / 系统 API 回调）；何时失效（generation、sessionId、runId、revision）。答不出的字段不配存在。
- **禁止推演合成：** 不用启发式猜测、时间/顺序推断、视觉行为反推造内部状态；不"顺路解读"别人事件里的未定义含义自创状态。
- **事件没到，状态就不出现：** "进行中"必须有确切的 run 承载，"有进度"必须有帧来源。不提前初始化"看起来合理"的中间态，不在无来源时显示假状态；宁可显示明确的空/未知。
- **失效与覆盖：** 异步状态一律携带失效凭据，迟到结果按凭据丢弃（榜例 interview reply 的 generation 过期丢弃）；覆盖必须按凭据单调（榜例 store revision 单调）；并发认领统一由 store 原子操作承担（榜例 `beginEphemeralRun`），不在各调用方自行持有并发判断。

## 5. 防御性代码预算（在边界校验一次，在核心信任类型）

- **必须校验的地方：** IPC 入口（`isWindowFromSender` + 载荷校验）、模型/HTTP 响应、文件/系统输入、跨进程队列出队。校验结果转成**稳定错误码**给产品层（如 `invalid-audio | queue-full | unauthorized` + `retryable`），不透传 HTTP body、堆栈、供应商字段。
- **必须不写的地方：** 模块内部复述类型系统的 guard——给刚由工厂产出的 branded id 再判空、给已收窄的 union 再判 undefined。需要运行时收窄通常说明上游漏了 `unknown`：修上游，不在下游多包一层。
- **catch 全部禁止裸吞：** 每个 catch 必须知道自己处理什么、转成哪个领域错误码；`catch (e) { console.warn(e) }` 然后继续跑是最常见的违禁写法；不确定能不能处理的错误向上抛。
- **fail-closed 优先于静默兜底**（榜例 `ime:prepare` 校验不过直接退出而非回落系统输入法；`pnpm dev` 端口冲突报错退出而非换端口）；"先用着、回头再处理"型防御一律删除。
- **资源防御写足（不算预算超支）：** 队列有界（榜例 interview 事件 bounded queue）、高频媒体走 credit 窗口（榜例 `INTERVIEW_AUDIO_CREDIT_BATCH`）、外部异步结果过期丢弃——这是防外部世界，不是防自己的代码。
- 用 `assert` 把"这里不可能"的前提写明，好过吞掉错误的 if。

## 6. 模块与抽象纪律

- **co-location：** 一个概念的代码在同一个文件/目录随它演进；改动一旦"必须同时碰五处才成立"，先怀疑布局，而不是加"同步修改"注释。
- **单 writer：** 同一状态只允许一个模块写（榜例多条 `ime-*-single-writer` Notes）；第二个写者出现之前必须先立端口。
- **抽象等第二消费者：** 第一个领域必须打通完整链路后，第二个领域真实复用时才抽底座（榜例：`answer-run` 单会话先跑通，`core/` 才随第二个领域出现）。第一位消费者不得预留、不得让 runtime 上移。
- **不建 `utils/` 大杂烩：** 工具函数与第一消费者共处，第二消费者出现才上提。
- **并行协作：** 稳定契约（类型、端口、事件）先合并，其余人按契约 + fake port 并行；不因适配他人未完成的模块而修改对方模块。改 `core/` 视为架构变更，走 Note。

## 7. 魔法值清零

- 常量提取且名字带单位与含义：榜例 `PCM_FRAME_MAX_SAMPLES = 1_600`、`PCM_FRAME_MAX_BYTES`、`INTERVIEW_AUDIO_CREDIT_BATCH`；数值语义放 JSDoc（"Target frame duration is 100 ms; the final frame may be shorter"）。
- **布尔实参必须具名：** `send({ frame })` 而非 `send(frame, true)`；内部形参也尽量对象化。
- 测试里的断言数字（采样偏移、字节数）可作为原始字面量出现，出现在业务流转里不允许。
- **同一语义字符串只在一处定义：** 错误码同表、频道名、事件 kind 的字面量全走类型。

# 下篇 · 写到什么程度

## 8. 规模预算：函数、文件、目录

模仿现有模式不等于设计判断；**"别的文件也这么长"永远不构成继续堆的理由。** 超预算必须拆，确需例外：代码注释写明"在拆什么、为什么先不拆"，并在 Note 留档。

- **函数：** 一个函数一件事。任一命中即拆——超过约一屏（40 行为参考线）；参数 ≥5；布尔实参 ≥2；按产品模式/来源切换的分支；同一函数声明两组互不相关的变量。"先接线后算法"用小函数组合表达，不是用注释分段。
- **文件：** 超过约 400 行必查多职责。榜例切法：算法（`pcmFrameValidator.ts`）独立于事件聚合（`turns/`）与线协议投影（`interviewProjection.ts`）；组合根（`runtime.ts`/`host.ts`）只接线；领域 contracts 不与协议 DTO 混写。
- **目录：** 单目录约 12 个文件起按子职责分目录（规划中：`interview/audio` → `vad` / `transcription` / `turns` / `reply`）。目录的目的是"三十秒找到该改哪里"，不是收纳美学。
- **追加即查：** 往已有文件加小段功能前，先问该文件是否仍是一件事、目录是否仍是清晰的域；目录结构照抄既有模式 ≠ 结构判断。

## 9. 可读性：团队成员互相读代码

- **文件顶部一行职责注释：** 它是干什么的、且不是干什么的（榜例 `protocol.ts`："desktop main ↔ agent worker 的线协议……只有这里出现在 utility process 边界"）。一文件一职责，文件名与职责同形。
- **注释写为什么、前提、取舍，不复述代码；** 控制流保持直白：短小的 `for-of`、直观分支，聪明一行流必须换成普通写法。
- **命名用领域词：** `turnCommitted`、`interviewerSource`；禁 `data`、`process2`、`handle1`；禁 `flag` 命名布尔。
- **不写聪明代码写常见代码：** 名字解释意图、JSDoc 解释契约、测试解释行为，三者任何位置齐全时，读者不需要读实现。

## 10. 测试：行为的证明

- **测试是可执行规格**：名字用行为句式（如 "keeps the single-active-run invariant when every store await spans real time"），读者只看测试名与断言便知契约。
- **一契约一测试**：稳定契约（类型、端口、协议）改动必有往返测试；打坏一个不变量之前必须有防回退测试压住（榜例：竞态修复为 single-active-run 不变量配的测试）。
- **失败要有断言：** UI 每个行为一个 test case（注入 mock bridge），失败走错码断言而非只测 happy path。
- **并发与异步的病要种进测试：** 用 deferred 让每个 await 都横跨真实时间，迟到丢弃、覆盖单调、认领原子性这些 bug 只在这种时间形态下可见。
- **不测实现结构：** 断言行号、私有变量、mock 内部次数不是规格；换实现不换行为时测试不许变。

# 终篇 · 落笔到提交

## 11. 门禁与提交纪律

- **全绿才提交：** `pnpm verify`（biome lint + 全包 typecheck + vitest + 架构守护）必须本地全过；CI 严格模式 `pnpm notes:check` 由管线执行，不可在本地用 `--no-verify` 跳过。
- **Note 配对：** 行为变化、契约变化、架构/流程变化、用户可见的变化在新变更里写新 Note 或更新既有 Note（记档流程按 `answra-change` skill 执行）；纯格式、机械重命名豁免。
- **秘密与工件：** `.env`、`*.log`、二进制、IME DLL 与词库不出现在 diff；发现即剔除，不能依赖 `.gitignore` 兜底。
- **diff 自审：** 提交前逐文件读自己的 diff——"写完"与"可 merge"之间的差值全部消灭在自审里；不夹带无关文件，不碰他人未完成的工作区，要动他人模块先沟通。
- **提交信息：** Conventional Commits（`feat|fix|docs|chore|refactor(scope): subject`），主题写行为变化而非文件清单；配套 Note 在正文中指档。

## 12. 过程与提交前自查十四问

写完读一遍；答不出的那问就是这一轮的 bug。

1. **每个前提是读出来的，还是推断的？** 推断的那条要么查证，要么停下来报告。
2. **四种强行手法**（杜撰接口、吞断链路、顺手重造、顺猜下游）用过哪一种？用过即停止写码，先报告。
3. 缺前置的需求，完整链路（需要什么、现状、代价）用产品语言列给用户了吗？
4. 代码落对层了吗？有没有沾各层的越界？
5. 新契约落成类型了吗？还是靠字符串/`unknown` 蒙混？
6. **每个被消费的状态字段答得出三问吗**（谁写、从哪来、何时失效）？有没有推演合成、无来源假状态？
7. 防御代码都在边界吗？核心有没有复述类型系统的 guard？
8. 有没有 catch-all、静默兜底、"先不过校验"路径？
9. 魔法值都命名了吗？同一语义字符串只有一处定义吗？
10. **函数/文件/目录超规模预算了吗？** 超了有注释理由与 Note 留档，还是顺手堆的？
11. 这次改动散落几个文件？是布局问题吗？
12. 文件顶部有一行职责注释吗？命名是领域词吗？
13. 行为有测试吗？"完成"叙述里的每一条都有证据吗？未决事实显式标注了吗？
14. 抽象到共享层：第二消费者在哪？第一消费者不应该预留。
