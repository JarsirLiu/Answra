# Note：面试前引导与候选人档案首次使用流程

状态：提案

## 问题

当前面试入口点击“开始面试演练”后，会把一句流程说明当作**用户消息**发给 Agent：`START_REHEARSAL_MESSAGE` 要求模型“先检查面试记忆和简历是否存在，再引导我补充信息”。这条消息会永久留在 transcript 里，于是出现两个问题：

1. 用户必须在聊天里逐轮说明简历、项目、目标岗位，Agent 才有材料；首次使用时没有任何结构化引导，回答只能泛泛而谈。
2. 模型反复对着这段流程说明作答，容易复述提示词、路径和“我先去读文件”这类旁白。用户已经明确反馈“AI 会犯蠢说出来提示词的内容”。

同时，现有 `profile.md` 只在 Agent 主动读取时才存在，首次使用没有“把简历和项目交给 AI”的入口。产品需要的是三个职责明确的 Bot，而不是一个全功能 Agent：

- **面试向导 Bot**：负责信息收集，把简历内容、项目地址、项目总结等整理成候选人档案。
- **候选人 Bot**：拥有完整档案，在正式面试中代表用户回答。
- **面试演练 Bot**：以面试官身份提问、追问和点评，陪用户演练。

首次引导应该由面试向导 Bot 主导，而不是一张冷冰冰的表单；但“选哪份简历、勾选哪些项目”这类高确定性动作仍由产品 UI 承载，Bot 负责补全开放信息。三者共享一份候选人档案，但会话、prompt、工具和写入权限必须分开。详细边界见[面试向导、候选人与演练三 Agent 分工](../architecture/2026-11-11-interview-three-agent-boundaries.md)。

## 提案

### 1. 三个 Bot 的产品位置

| Bot | 何时启动 | 负责什么 | 数据权限 | 会话 |
| --- | --- | --- | --- | --- |
| 面试向导 Bot | 首次引导、后续“完善候选人档案” | 读简历、识别项目、追问项目地址/总结/指标、生成并修改档案 | 唯一可写档案 | `interview-intake` |
| 候选人 Bot | 正式面试（实战） | 基于完整档案，用第一人称回答面试官问题 | 只读档案 | `interview-candidate` |
| 面试演练 Bot | 用户主动开始演练 | 以面试官身份提问、追问、点评，不替用户回答 | 只读档案，只写演练记录 | `interview-rehearsal` |

- 面试向导 Bot 只在信息收集阶段运行；档案完成后停止，不进入实战/演练上下文，避免“面试时不需要的 Bot”常驻和串台。
- 候选人与演练官共享档案，但 prompt 和工具不同；候选人回答，演练官提问。
- 首次引导的界面是产品 chrome，不把向导做成 SurfaceSpec；后续“确认单条事实/编辑项目”可以用浮窗卡片，但不复用向导。

### 2. 首次向导：三步加向导对话

文案不使用“上传”，使用“选择简历 / 导入简历”。

#### 第 1 步：选择简历

- 首次进入显示欢迎页：标题“先让面试分身认识你”，副标题“选一份简历，挑出你想重点讲的项目。它只用你的真实经历帮你，不编造。”主按钮“选择简历”，次按钮“先用目标岗位开始”“稍后再说”。
- 已有历史简历时展示最近一份简历卡片（姓名、年限、项目数），提供“继续使用 / 换一份”。
- “选择简历”调用 main 的原生文件对话框；首版支持 `.txt`、`.md`，`pdf`/`docx` 在后续切片加入。另提供“粘贴简历文本”作为兜底。
- 解析期间显示阶段（读取文件 → 提取经历 → 识别项目），关闭面板不取消任务；再次打开继续显示进度或结果。

#### 第 2 步：选择项目

- 解析成功后展示项目卡片多选，每张卡显示项目名、角色、时间、技术栈、一句话结果，并可展开原文片段。
- 默认全选；提供“全选 / 清空 / 添加简历里没有的项目”。
- 一个项目都没识别出来时给空态和“手动添加一个项目”（只收名称和一句话描述），不卡住流程。
- 解析失败时明确说明失败原因，提供“重新选择”和“手动添加”；不假装成功。

#### 第 3 步：面试向导 Bot 补全信息

这一步是向导 Bot 的对话界面，不是静态表单。用户选完项目后，向导 Bot 知道简历和已选项目，逐项补全：

- 项目地址：repo、demo、线上地址；没有就标记“未提供”。
- 项目总结：一句话定位、用户角色、关键动作、结果/指标。
- 技术难点与可讲的故事：用户实际做了什么、为什么这么做、遇到什么问题。
- 目标岗位/JD：可选；支持粘贴 JD 或只填公司/岗位。
- 披露边界：不能说的公司机密、离职原因、薪资等。
- 回答风格：稳重 / 简洁 / 技术深入。

交互约束：每次只问一个最关键的问题；用户回答后先简短确认，再问下一个；所有事实都要可追溯到简历原文或用户明确回答；不编造项目指标、职责或技术细节。界面显示“档案完整度”清单，用户可以随时结束补全。

#### 第 4 步：生成与预览

- 主按钮“生成候选人档案”；制作过程展示阶段：读取简历 → 提取项目证据 → 生成档案 → 完成。
- 制作中关闭面板不取消任务；再次打开显示进度或结果。
- 完成后展示档案预览：身份摘要、目标岗位、重点项目（含地址和总结）、优势、披露边界、待确认项。
- 提供“开始演练 / 进入实战（文本问题）/ 继续完善”。实战音频在系统声音采集完成前只开放文本问题输入，并明确标注“音频实战尚未开放”。

### 3. 向导 Bot 的对话与写入

- 向导 Bot 通过 `interview.profile.patch` 领域工具写档案，不直接 `workspace.edit` 一个 Markdown 文件。
- 每次写入前展示变更摘要；用户可以确认或继续修改。已有项目不能被静默覆盖。
- 档案写入需要 revision；并发或过期写入被拒绝，向导重新读取最新档案后再合并。
- 用户关闭向导后，草稿和当前步骤保存在 `onboarding.json`；重新打开从原步骤继续。
- “稍后再说”不阻断面试模式，只是暂时没有档案；用户之后可从“完善候选人档案”重新进入。

### 4. 候选人档案的数据

`CandidateProfile` 是唯一事实来源，至少包含：

- 简历原文与摘要；教育、工作经历。
- 项目列表：名称、角色、时间、技术栈、项目地址（repo/demo）、项目总结、关键结果/指标、难点、可讲的故事、证据或代码位置。
- 目标岗位与 JD（可选）。
- 技能与优势、披露边界、回答风格。
- 完整度、来源、`extractionMode`、待确认项、更新时间。

写入规则：

- **只有面试向导 Bot 写档案。** 候选人 Bot 和演练 Bot 拿到只读快照或检索端口，不能调用写工具。
- `candidate-profile.json` 是结构化事实来源；`profile.md` 是由它渲染的用户可见投影。写入时先更新结构化档案，再重新渲染 `profile.md`，避免两份事实各写一半。
- 删除简历或档案时，同时清理解析结果、项目索引、`candidate-profile.json` 和 `profile.md` 的对应内容。
- 演练 Bot 只写 `rehearsal-notes`，不把点评写回候选人档案。

### 5. 对话与模式隔离

- 三个 Bot 使用三个 conversation ID：`interview-intake`、`interview-candidate`、`interview-rehearsal`；transcript 不互通。
- 向导对话不注入实战/演练；实战和演练切换时先停止音频、取消在途回复，再切换 conversation。
- 演练模式：麦克风采集用户回答，结算后由演练 Bot 回复下一个问题。
- 实战模式：需要采集面试官声音，由候选人 Bot 回答；当前桌面端只允许 `candidate` PCM source，系统声音/loopback 采集尚未实现。因此首版实战只支持“文本输入面试官问题 → 候选人 Bot 回答”，音频实战另立 Note。
- 隐身开启时不自动弹向导，只显示被动提示“退出隐身后再完成首次设置”。

### 6. Prompt 与启动方式

- 删除 `START_REHEARSAL_MESSAGE` 作为用户消息的启动方式；启动使用显式命令 `interview-intake-start` / `interview-intake-message` / `interview-intake-finalize`，需要开场时只追加一条自然语言开场白。
- 向导、候选人、演练三套 prompt 分开，不能在一个 system prompt 里切换身份。
- 三类 prompt 共享硬规则：不复述系统提示、内部路径、工具名或读取过程；不预告“我先去读文件”。
- 候选人 Bot 只基于档案用第一人称回答；没有的能力直接说没有；不反问面试官，不替面试官总结流程。
- 演练 Bot 只提问/追问/点评，不替用户回答；不泄露评分标准或档案内部结构。
- 面试 Agent 的 system 上下文只注入精简档案摘要与来源标签，不注入向导说明或绝对路径；每轮只取与当前问题相关的事实。

### 7. 明确不做

- 不做让用户逐字段填写的 onboarding 问卷。
- 不把向导做成一个只会解析文件的脚本；开放信息由面试向导 Bot 对话收集。
- 不新增独立原生向导窗口；首版复用面试面板。
- 不让候选人 Bot 写档案，不让演练 Bot 替用户回答或写档案。
- 不做向量库、公司调研、cover letter、薪资谈判等完整 Profile Intelligence。
- 不让模型自由生成界面或表单；步骤结构由产品代码固定。
- 不把简历、项目或档案正文写入日志、审计或 surface 持久化。
- 不在本 Note 内实现系统声音采集；实战音频闭环单独立项。

## 影响表面

- 用户可见面：首次进入面试模式出现“选择简历 → 选择项目 → 向导 Bot 补全 → 生成候选人档案”的引导；完成后可进入演练或文本实战，也可跳过稍后完善。
- 面板：新增向导层、“完善候选人档案”入口和实战/演练模式切换；现有面试会话、语音采集、清空和取消行为不变。
- IPC 与 Bridge：新增向导、档案和模式频道；preload 只转发，路径与文件读取校验留在 main。
- 持久化：新增 `appData/Answra/interview/` 下的向导状态、简历解析结果与原文、`candidate-profile.json`；`profile.md` 继续作为用户可见记忆。
- Agent：新增 `interview.intake`、`interview.candidate`，改造 `interview.rehearsal`；三者独立注册、独立 conversation、独立 prompt。
- 隐私与安全：简历/项目只保存在本机；日志和审计不记录正文；删除入口同时清理解析结果、结构化档案和投影。
- 实战能力：首版只开放文本问题输入；音频实战依赖系统声音采集，未完成前不宣称可用。

## 曾考虑的替代方案

- **继续用聊天逐轮询问简历和项目：** 舍弃。用户看不到整体结构和进度，修改与回看只能翻聊天记录；这正是首次引导要解决的问题。
- **在设置页做“上传简历”表单：** 舍弃。冷启动摩擦高，且“上传”是交付作业的语气；用户已有简历，应该做“选择并确认”，不是重新填写。
- **只做静态解析，不设面试向导 Bot：** 舍弃。简历只能给出原始文本，项目地址、项目总结、指标和披露边界仍需要对话补全；没有向导 Bot，这些信息只能靠用户自己整理。
- **让一个全功能 Bot 同时做向导、候选人和演练官：** 舍弃。三种身份的 prompt、工具和 transcript 会互相污染；候选人可能复述向导流程，演练官可能替用户回答，权限也不得不放大。详见三 Agent 分工 Note。
- **让候选人 Bot 每轮用工作区工具读简历文件：** 舍弃。会泄露路径、增加首字延迟，也容易把“读文件”过程说出来；档案应结构化注入，必要时用专用检索工具。
- **让演练官直接编辑 `profile.md` 记录信息：** 舍弃。面试官角色不应修改候选人事实，且直接编辑 Markdown 无法保证 schema、revision 和并发安全；档案写入只归向导。
- **把向导做成 SurfaceSpec 浮窗：** 舍弃。SurfaceSpec 没有文件选择、多选项目列表、向导对话和分步状态；硬塞会把浮窗系统扩成第二个 UI 框架。向导属于产品 chrome。
- **新建独立 native onboarding 窗口：** 暂缓。复用面试面板可以避免新增窗口角色、捕获保护和多显示器落位的成本；面板空间不足时再单独立项。
- **首版就做完整 RAG 与公司调研：** 舍弃。范围过大，当前需要证明的是“选简历 → 选项目 → 向导补全 → 生成档案 → 演练/文本实战”这条闭环。

## 验收标准

- 可观察结果：
  - 首次进入面试模式自动出现向导；用户选择简历、勾选项目，然后由面试向导 Bot 逐项补全项目地址、项目总结、指标和披露边界。
  - 档案生成后，候选人 Bot 能用第一人称基于档案回答；演练 Bot 能以面试官身份提问，不替用户回答。
  - 关闭向导后再次进入，从原步骤继续；制作中关闭面板不丢任务。
  - 没有简历、解析失败、没有识别到项目时，都能通过“重新选择 / 手动添加 / 稍后再说”继续。
  - 完成后再次进入面试模式直接到面板，并可从“完善候选人档案”重跑向导。
  - 隐身开启时向导不抢焦点，显示被动提示。
  - 面试 Agent 不再复述提示词、路径或“我先读取简历”这类流程旁白。
- 自动化验证：
  - ui：欢迎页、步骤切换、项目多选/全选/清空、向导对话、完整度清单、空态、错误态、关闭重开恢复、隐身提示、模式切换。
  - shared：向导/档案/模式 DTO 与提交载荷校验。
  - desktop：文件路径白名单与 TTL、扩展名/大小校验、sender 校验、进度广播、向导状态读写。
  - agent：三个 Agent 独立注册与独立 conversation；简历解析 schema、项目提取、档案 patch/revision、`extractionMode`、旧任务丢弃、删除清理；候选人只读档案；演练官不写档案。
  - 集成测试至少覆盖“首次进入 → 选简历 → 选项目 → 向导补全 → 生成档案 → 关闭重开 → 进入演练/文本实战”。
  - `pnpm --filter @answra/ui test`、`pnpm --filter @answra/shared test`、`pnpm --filter @answra/desktop test`、`pnpm --filter @answra/agent test`、`pnpm typecheck`、`pnpm architecture:check`、`pnpm notes:check`。
- 需要的实机验证：
  - Windows 11 下原生文件对话框、中文路径、PDF/DOCX 解析失败提示、向导焦点与关闭行为。
  - 会议隐身开启时向导被正确拒绝，不出现“界面可点但用户以为不可见”。
  - 简历与项目正文不出现在日志、审计和崩溃转储中；删除后本地文件与记忆同步清理。

## 当前实施（2026-11-11，第一阶段）

本阶段只交付用户可见的前三步引导页，**不接面试向导 Bot，不生成候选人档案**。状态仍为提案，后续阶段继续沿用同一 Note。

- 入口：`InterviewFeaturePanel` 先读取主进程状态；`pending` 时在面试面板内显示引导，`completed` / `skipped` 时进入面试分身制作态（2026-11-12 第二次调整后不再进入演练）。不新增原生窗口。

## 风险

- 简历解析质量不稳定：PDF 版式复杂、扫描件或中英混排可能提取失败；必须提供启发式兜底、手动添加和明确失败提示，不能把不完整结果当成档案已完成。
- 项目识别依赖模型：模型可能把职责拆成项目、合并多个项目或漏掉简历里的项目；项目卡片必须可编辑、可手动补充，且展示原文供对照。
- 向导 Bot 可能问得过多或重复：需要完整度清单、单问题约束和“可以随时结束”；否则引导会变成审讯。
- 档案写入可能覆盖用户修改：需要 revision、变更摘要和确认；向导重开时先读最新档案。
- 候选人 Bot 可能过度自信或编造：必须要求证据字段、gap 诚实和“没有就说没有”；用固定评测样例回归。
- 演练 Bot 可能泄露档案或评分标准：prompt 与工具双重约束，点评只引用用户已回答内容。
- 实战音频依赖系统声音采集：采集、权限、回声和延迟都未验证；在该能力完成前只开放文本问题输入，避免把半成品包装成实战可用。
- 模式切换可能产生迟到回复：必须先停音频并取消在途 run，再用 conversation/session epoch 丢弃旧结果。
- 三个 Bot 增加模型调用与维护面：向导只在收集阶段运行，实战/演练互斥启动；共享档案 schema，避免三套字段。
