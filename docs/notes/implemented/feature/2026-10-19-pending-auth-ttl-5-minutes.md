# Note：桌面端登录待处理 state 的 TTL 从 2 分钟延长到 5 分钟

状态：已实施

## 问题

桌面端登录采用 PKCE + 浏览器授权：`login()` 落盘一次性 `state`（`PENDING_AUTH_TTL_MS` = 2 分钟）后打开站点授权页。实测联调（Windows 10，本地 dev）中，用户在站点完成登录/注册、再回到授权卡片点「允许」，整窗超过 2 分钟时回调被 `expired` 拒绝，且桌面端 UI 无任何反馈（只在日志里），用户反复尝试都"看起来没发生"。站点侧 `callbackUrl` 机制本身工作正常，失败全部来自桌面端 pending 过期。

## 影响范围

- 用户可见行为：桌面端「登录」打开的浏览器授权窗口时长从 2 分钟变为 5 分钟；超过后仍静默作废，回到桌面端重新点「登录」即可重来。
- 不改变：桌面端本地凭据存储、站点会话 Cookie 生命周期、网关兑换接口语义。

## 涉及范围

- 代码/模块：`apps/desktop/src/main/auth/pendingAuth.ts`（`PENDING_AUTH_TTL_MS` 2 分钟 → 5 分钟，注释同步）。
- 测试：`apps/desktop/test/authService.test.ts`、`apps/desktop/test/authPendingAuth.test.ts`（断言以常量推导，自动跟随）。
- 用户行为变化：浏览器授权窗口从 2 分钟放宽到 5 分钟。

## 影响表面

- 设置面板「账户 → 登录」打开的浏览器授权窗口：从 2 分钟放宽到 5 分钟，期间完成的回调正常消费。
- 超过 5 分钟的回调仍静默作废；用户回到桌面端再次点「登录」即可重新发起（每次发起作废旧请求，无数量限制）。

## 决定

TTL 调整为 5 分钟。保留约束不变：同时只允许一个待处理登录、`state` 单次使用、`redirect_uri` 必须一致、过期回调一律拒绝；再次点「登录」会作废旧 pending 并重建（失败后重新点登录始终可用，`apps/desktop/src/main/auth/authService.ts` 的 `clearPending` / `closeActiveCallback` 路径已有测试覆盖）。

## 曾考虑的替代方案

- **保持 2 分钟、在过期时向 UI 显式提示：** 舍弃。正确但在新用户首次登录（要在站点输入账密、可能 2FA）场景中窗口仍然太紧；提示属于交互增强，另行评估，不与 TTL 调整绑定。
- **把 TTL 取消（无过期）：** 舍弃。长挂起的授权标签页被劫持回放的风险窗口变成无限大，违反"一次性 state 短时效"的既有安全约束。
- **把 TTL 做成站点 configurable：** 舍弃。目前只有桌面 main 进程使用该值，加配置面没有第二消费方，属过度设计。

## 后果与防回退

- 劫持回放窗口从 2 分钟放宽到 5 分钟；一次性 `state` 且单 pending 的约束仍在，回放仍被 `unknown-state` / 重放拒绝兜底。
- 若未来再调 TTL，必须同步评估站点登录页（含注册、2FA）所需的真实停留时长，不能单方面回退到 2 分钟。
- 过期回调仍是静默拒绝（日志有 `expired` 记录）；"过期后 UI 提示重新登录"是后续候选项，实施时需另写 Note。

## 验证

- `pnpm --filter @answra/desktop test -- authPendingAuth authService` 通过（TTL 断言走常量，无硬编码 2 分钟）。
- Windows 本地联调实测（`http://127.0.0.1:3100` 站点 + `:8080` 网关）：修复站点 dev 资源拦截问题后，完整链路「桌面端发起 → 站点登录 → 授权卡片点允许 → 环回回调 → 网关 exchange 200」走通；先前 2 分钟窗内未完成的尝试确实因 `expired` 被拒，与本 Note 问题一致。
