# Note：桌面端会员能力目录

状态：已实施

## 问题

桌面端登录后需要展示当前会员档位和实际可用的云端能力。客户端请求 `/api/v1/capabilities`，但 AnswraSite 网关此前没有该接口，导致会员档位恒为空、能力目录无法读取。

## 涉及范围

- 代码/模块：Answra `apps/desktop/src/main/auth/authService.ts`；AnswraSite `gateway/internal/handler/subscription_handler.go`、`gateway/internal/server/routes/user.go`。
- UI/进程/协议/持久化表面：网关通过已认证用户身份查询有效订阅；桌面 main 拉取目录并将不含 token 的 `plan`/`capabilities` 状态交给 UI。没有新增持久化结构。
- 相关 Note：[桌面端账号登录与凭据（Phase 0）](../feature/2026-10-17-desktop-account-login-and-credentials.md)、[桌面端公告中心](../feature/2026-10-17-desktop-announcement-center.md)。

## 决定

- 新增认证的 `GET /api/v1/capabilities`。无有效订阅或套餐组已停用时返回 `plan: null`；存在有效订阅时返回按 `Accept-Language` 本地化的套餐组名。
- `capabilities` 只返回桌面端确实可以调用的云能力。当前桌面端尚无云模型调用入口，因此返回空数组，不因订阅有效就虚构已解锁能力。
- 桌面端保持现有职责：登录兑换成功后拉取目录，目录暂时不可用不清除 token；恢复有效登录态时重新拉取目录。能力列表只用于展示，未来云端入口必须在服务端单独检查订阅与额度。
- 登录 authorize/exchange 已在 AnswraSite 网关实现，本次不重做登录协议、授权码存储或 token 生命周期。

## 影响表面

- 新增 `GET /api/v1/capabilities` 用户 API，复用网关 JWT、后端模式守卫和用户级限流中间件。
- 桌面账户区可显示套餐名称；当前能力数为零时继续显示无可用云能力，不影响本地功能和账号登录。

## 曾考虑的替代方案

- **把会员字段并入 `/api/v1/auth/me`：** 会员/能力目录与用户资料的查询和更新节奏不同；独立接口对应桌面客户端已采用的路径，也避免改变现有 profile 响应契约。
- **客户端按套餐名自行映射能力：** 套餐到能力的映射会随客户端版本固化，且客户端不能权威判断订阅撤销；舍弃，能力必须由服务端返回。
- **先把未来能力 ID 返回给有订阅的用户：** 当前无对应桌面云端调用入口，会造成 UI 显示解锁但功能不可用；舍弃，待云端调用接口落地时再逐项登记。

## 后果与防回退

- 网关是套餐名称和能力目录的权威来源；客户端不得从本地套餐名推导权限。
- 有效订阅不等于桌面云能力可用。新增能力时需同时实现服务端调用入口、服务端订阅/额度校验、能力目录返回值和对应测试。
- 当前能力目录故意返回空数组；不能据此认为桌面云模型调用或云端门禁已完成。

## 验证

- 网关 handler 测试覆盖有有效套餐、无有效套餐、忽略停用套餐和订阅读取失败。
- Answra 桌面 `authService.test.ts` 已覆盖目录响应解析、登录后拉取、恢复登录态重新拉取、目录失败不影响登录。运行结果记录在本次实现验证中。
- 仍需部署后在 Windows 桌面端通过网站登录回跳，确认线上网关返回套餐名称并与网站订阅一致。

## 风险

- 用户可有多条有效订阅；当前按网关仓储返回顺序（创建时间倒序）选择第一个仍启用的套餐组显示。能力权限不依赖此展示选择。
- 桌面端暂无云能力入口，能力数组为空是当前产品状态的准确反映。
