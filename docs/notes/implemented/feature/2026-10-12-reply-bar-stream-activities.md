# Note：回复条展示标准消息活动

状态：已实施

## 问题

截图分析目前只提取文本 part 展示。模型长时间输出 reasoning 或发出工具事件时，回复条看起来像空白，用户无法判断运行进度。

## 涉及范围

- 代码/模块：`packages/shared/src/channels.ts`、`packages/ui/src/app/useConversationChat.ts`、`packages/ui/src/app/useReplyWorkflow.ts`、`packages/ui/src/components/panels/ReplyBar.tsx`、`packages/ui/src/components/panels/ReplyActivityTicker.tsx`、`apps/desktop/src/main/ipc/windowIpc.ts`
- UI/进程/协议/持久化表面：标准 AI SDK UI message chunk 到回复条活动视图的投影；活动仅在当前 renderer 内存中存在，并经现有窗口状态 IPC 同步。

## 决定

- 回复条接收按顺序组织的活动条目，区分思考、文本、工具、状态、来源/文件与错误。处理阶段快速轮播活动；文本回答开始后，ticker 只展示当前连续文本阶段并从开头缓慢跟随，避免左侧“回答”图标对应到仍在滚过的思考内容。完整活动仍保留在本轮内存状态中。
- reasoning/text delta 归并到对应活动条目；工具 input、output、error 分别显示工具名和可读摘要。
- 运行中没有可见内容时展示阶段提示；正文继续生成时仍同时保留思考和工具活动，完成时保留整轮活动供查看。
- 这是展示协议的投影，不新增工具执行、结构化答案或持久化能力。

## 影响表面

- 回复条：标准活动以单行横向滚动显示，左侧图标标记当前阶段。思考和文本图标保持静态，思考正文用斜体和紫色，文本回复用蓝色区分且不显示额外“回答”标签；过程活动为 140px/s，文本为 100px/s。文本阶段生成时跟随，结束后从答案开头滚动至末尾，完整展示长回复。根因和回归约束见[回复条终态答案滚动与活动标签](../bug-fix/2026-10-12-reply-bar-final-answer-scroll.md)。
- 流式布局：横向 ticker 弹性占宽，停止/发送与关闭按钮组成不可压缩的固定操作组，顺序与编辑态一致。
- 独立回复窗口：现有窗口状态 IPC 同步活动列表与文本、错误、附件状态。
- IPC 边界：main 进程验证活动类别、字段类型和可选错误/等待状态。
- 截图对话：reasoning 和工具事件可见，但不改变 runtime 当前是否配置工具的行为。

## 曾考虑的替代方案

- **只在文本为空时展示思考：** 会在正文开始后隐藏此前分析与工具活动，不利于判断运行过程，因此保留本轮完整活动。
- **把所有 chunk 序列化成原始 JSON：** 对用户不可读且暴露实现细节，因此转换成少量稳定的展示类别和摘要。

## 后果与防回退

- 新增 AI SDK chunk 类型时，回复条应有稳定可读的类别或通用状态回退，不能静默丢弃非文本活动。
- 活动内容不得参与操作组测宽；按钮需保持固定尺寸与稳定顺序。
- 活动 ticker 只允许横向溢出，不能因事件累积改为纵向滚动或撑高窗口。
- 只有等待状态图标可旋转；思考和文本回复标识保持静态。文本活动跟随速度须显著慢于过程活动，避免最终回复在窄回复条中掠过。
- 文本回答成为当前阶段后，不得让之前的思考/工具活动残留在 ticker 可视区并与回答图标、颜色错配；此前活动仍保存在本轮内存数据中。
- 活动流不记录到持久化存储；错误正文仍按纯文本处理。
- 工具事件展示不代表本应用已经配置或执行相应工具。

## 验证

- 自动化测试覆盖 reasoning/text 合并、工具生命周期以及多活动向回复条状态的传递。
