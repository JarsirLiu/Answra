# Note：隐身模式内置中文键盘方案否决

状态：已拒绝：renderer 自绘拼音键盘不能替代系统级正常中文输入

## 问题

隐身模式需要避免 Windows 和 macOS 系统输入法的候选窗口被会议软件捕获。此前尝试用拼音引擎加 renderer 自绘键盘，期望在应用内完成中文输入。

## 涉及范围

- `packages/ui` 的隐身对话输入行为、候选词 UI 和输入法依赖。
- `@goliapkg/pinyin` 依赖、WASM 资源、适配层和组件测试。
- 未来所有隐身对话页面的输入能力设计。

## 提案

否决 renderer 自绘拼音键盘作为“正常键盘打字”的实现。该方案只能处理拼音串和应用内候选选择，不能接管操作系统键盘输入法的完整行为，也不能提供用户期待的系统级中文输入体验。实验代码和依赖必须移除，恢复现有输入路径。

隐身模式如果继续禁止系统 IME，必须明确产品行为是“禁止文本输入”，不能用屏幕键盘或按键事件伪装成正常中文输入。重新引入输入方案前，必须先证明 Windows 和 macOS 上可以接收物理键盘、完成候选组合与上屏，并且候选窗口不会被共享捕获。

## 曾考虑的替代方案

- **renderer 自绘拼音键盘：** 舍弃。它依赖应用内拼音缓冲和候选选择，不是系统输入法替代品，且交互与用户要求不符。
- **直接使用第三方 Web Component 输入法：** 舍弃。仍受浏览器 IME、Shadow DOM 和平台输入法行为限制，不能保证共享画面安全，也无法保证完整中文输入体验。
- **继续使用系统输入法：** 仅适用于普通模式。隐身模式下系统候选窗口可能被会议软件捕获，不能作为隐身输入策略。
- **原生平台输入法桥接：** 保留为未来重新评估方向。需要分别实现 Windows TSF/IMM 和 macOS NSTextInputClient 等平台能力，验证窗口捕获边界、焦点和生命周期，不能由当前 renderer 组件直接替代。

## 否决理由

该实验把“能在 renderer 内输入拼音”误当成“替代系统输入法的正常打字”。它不能处理系统级组合输入、候选窗口、焦点和平台输入法协议，因此不满足用户目标。

## 后果与防回退

隐身模式暂时不提供中文文本输入；普通模式继续使用系统输入法。未来若要恢复隐身输入，必须新增平台能力设计、Windows/macOS 实机验证和独立的安全边界 Note，不能重新接入本次自绘键盘实验代码。

## 模块边界

当前 `packages/ui` 只负责现有对话输入和隐身输入保护，不持有拼音缓冲、候选算法或虚拟键盘状态。未来原生输入法桥接应归入 `desktop` 平台能力，通过明确的 shared 契约供 UI 调用，不能让 renderer 直接访问 Electron 或操作系统输入法 API。

- 已移除 `@goliapkg/pinyin`、WASM 适配层、`VirtualPinyinKeyboard` 组件及其测试。
- 已移除对话面板中 `readOnly`/`inputMode="none"` 的实验键盘接入，避免把按键事件方案误认为正常输入。
- `pnpm notes:check`、UI typecheck、UI tests、桌面 typecheck/build 和 `pnpm verify` 必须作为本次撤销的提交门禁。
- 后续代码评审不得以“屏幕按键可输入”作为隐身中文输入完成标准；验收必须覆盖物理键盘和平台输入法组合行为。
