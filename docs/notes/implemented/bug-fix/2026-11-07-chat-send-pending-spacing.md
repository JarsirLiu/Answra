# Note：对话发送等待态与消息区间距

状态：已实施

## 问题

普通对话发送后，IPC 返回前没有 assistant 消息或执行事件；这段时间不应把请求误显示成模型运行。Agent 返回 snapshot 并确认 run 已建立后，真实执行事件才开始驱动思考 UI。执行事件到达后，最后一条 AI 消息又贴近输入框。

## 涉及范围

- 代码/模块：UI ChatPanel、共用消息流样式、FloatingBarApp 行为测试
- UI/进程/协议/持久化表面：普通对话等待视觉状态和消息区布局；不改 Agent 事件协议或 transcript

## 根因

现有 `sending` 只禁用了 composer，没有对应的视觉运行提示。Agent 的真实 run 及思考事件要等发送 IPC 返回后才可被 snapshot 接入，因此这段等待不能使用思考状态。消息流底部内边距只有 10px，最后一条消息与 composer 的 12px 外边距视觉上紧贴。

## 修复

- IPC 返回前只保留发送中禁用态和草稿；不创建 transcript 消息或伪造思考事件。
- Agent 返回的 snapshot 含 `activeRunId` 后，UI 投影将对应消息标为等待流活动；现有 run 事件和思考组件负责后续状态。
- 普通对话消息视口底部增加 8px 留白；共用消息流和面试面板不受影响。

## 曾考虑的替代方案

- **提前显示“思考中”：** IPC 尚未建立可识别 run 的执行状态，显示思考会伪造事件语义，因此舍弃。
- **IPC 返回前显示无文字运行图标：** 会把尚未被 Agent 接受的请求误报成运行中，因此舍弃。
- **扩大所有 conversation 视口底部间距：** 会同时改变面试面板布局；改用 ChatPanel 专属修饰类。

## 决定

- 运行图标只能由 Agent 返回 snapshot 的 `activeRunId` 或真实运行/流事件驱动；IPC 等待不是模型运行状态。
- 该请求态不写入 transcript，也不映射为 `reasoning-start`；snapshot 到达后显示运行图标，真实执行事件到达后由事件驱动的思考 UI 接管。
- 增加消息视口底部内边距，保证最后一条 AI 消息与 composer 有稳定间隔。

## 验证

- UI 测试覆盖延迟发送期间保留草稿、snapshot/真实事件到达后的状态切换及专属消息流样式。
- `pnpm verify` 与 `pnpm notes:check` 作为提交门禁。

## 后果与防回退

- 等待图标表示 Agent 已接受 run 但尚未发出流活动，不进入消息记录，也不代表模型已开始推理。
- 回归测试使用延迟 send IPC 和事件先到的场景，确认响应前无图标，snapshot 恢复后显示，首个流事件后由思考 UI 接管。
- 普通对话的底部间距通过专属 class 限定，避免污染共用消息流的其他消费者。
