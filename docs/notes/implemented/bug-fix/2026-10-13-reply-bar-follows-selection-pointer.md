# Note：回复条跟随截图结束指针

状态：已实施

## 问题

截图框选结束后，回复条原来按选区矩形底边中心定位。选区较大或拖拽方向反向时，回复条会离开用户最后松开鼠标的位置，造成每次截图后都像跳到固定位置。

## 根因

框选 overlay 只上报选区矩形，没有保留有效 `mouseup` 的坐标；回复条只能从矩形推导底边中心，因此无法跟随用户最后的指针位置。

## 修复

新增 `RegionSelection.point`，由 overlay 在有效 `mouseup` 时上报。主进程用 `point` 定位回复条，用 `rect` 独立完成截图裁剪，并继续执行工作区边界 clamp。

## 涉及范围

- `packages/shared` 的区域截图 IPC 契约
- `apps/desktop` 框选 overlay、截图编排和回复条定位
- Windows 多显示器工作区内的回复条落位

## 决定

`RegionSelection` 同时携带用于裁剪的 `rect` 和用于交互定位的 `point`。框选 overlay 在有效 `mouseup` 时上报最终指针点；主进程继续使用 `rect` 截图，但回复条使用该点作为锚点，并通过工作区 clamp 保证完整窗口可见。

## 曾考虑的替代方案

- **继续使用选区中心或底边中心：** 几何上稳定，但不符合用户对“截图最后位置”的预期，因此舍弃。
- **在主进程重新读取系统鼠标位置：** 会引入平台 API 和时序竞态，无法保证读取到截图结束瞬间的点，因此舍弃。
- **让 overlay 只上报点、主进程反推截图矩形：** 会把裁剪正确性绑定到定位数据，拖拽反向和边界 clamp 容易产生偏差，因此舍弃。

## 后果与防回退

- `point` 与 `rect` 使用同一 overlay 坐标系，必须保持相对目标显示器左上角的逻辑像素语义。
- 回复条定位不得改变截图裁剪矩形；两者是独立职责。
- 多显示器和边缘位置仍必须经过工作区 clamp。

## 验证

- `windowLayout` 覆盖指针锚点、边缘 clamp 和显示器原点。
- `captureIpc` 覆盖选区对象完整传递到回复条锚点。
- Desktop 类型检查和相关 Vitest 测试通过。
